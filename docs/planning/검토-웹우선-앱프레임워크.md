# 검토 — SEO 웹 우선 출시와 앱 프레임워크 선택 (지금문연)

> 작성일: 2026-10-18 · 대상: [세부계획-병원약국](세부계획-병원약국.md) §1(형태), §6(시스템), §8(로드맵)
> 질문: ① SEO를 고려한 반응형 웹을 먼저 만들고 앱으로 넘어가는 순서가 맞는가 ② 앱은 네이티브, Flutter, 다른 옵션 중 무엇으로 만들 것인가

---

## 결론

1. **웹 우선 → 앱 순서는 맞다.** 이 서비스의 수요는 명절·심야에 터지는 스파이크형이고, 그 순간 사람들은 앱을 설치하지 않고 검색한다. 앱은 고객을 데려오는 채널이 아니라 한 번 온 사람을 붙잡는 장치(알림·위젯·즐겨찾기)다. 다만 두 가지를 고쳐야 한다.
   - **2027년 설 연휴는 2월 6~9일**이다(세부계획의 '2월 중순'은 오류였고 2026-10-18에 날짜만 고쳤다). 새 도메인은 검색 색인과 순위가 잡히는 데 수 주에서 수 개월이 걸리므로, **검색용 페이지는 MVP 기능보다 먼저, 11월 중순까지 공개**해야 한다.
   - 앱 개발 착수는 날짜가 아니라 **설 연휴 실측 지표로 결정**한다(§4).
2. **앱 프레임워크는 React Native(Expo)를 권한다.** 웹을 Next.js(TypeScript)로 만들면 같은 언어로 타입·API 클라이언트·확인 루프 로직을 공유할 수 있고, 스토어 심사 없이 앱을 고치는 OTA 업데이트가 기본 제공되며, 이 앱의 화면은 리스트·지도·전화 버튼이라 네이티브 성능의 이점이 작다. **Flutter는 차선**(팀이 Flutter에 익숙한 경우), **네이티브는 현 단계에서 과하다**, **웹뷰 래핑은 임시 실험용**이다.

## 1. 왜 웹이 먼저인가

| 근거 | 내용 |
|---|---|
| 수요 순간의 행동 | "일요일 밤 소아과", "설날 문 여는 약국"을 검색한다. 설치는 급한 순간의 장벽이다 |
| 공식 앱의 실패 사례 | 응급똑똑은 2025년 추석 직전 정부 안내문자를 보고 설치한 사람들이 접속 장애를 겪어 리뷰 27건이 몰렸다([리뷰 분석](응급똑똑-리뷰-분석.md)). 설치를 요구하는 순간 첫 경험이 깨질 위험이 커진다 |
| 공유 구조 | 가족 단톡방에 보낸 링크가 설치 없이 바로 열린다. P3(고령 부모와 보호자 자녀) 시나리오와 바이럴 루프가 웹에서 가장 짧다 |
| 비용 | 웹 하나로 iOS·Android·PC를 모두 덮는다. 스파이크형 수요라 평시 고정비를 낮게 유지해야 한다 |
| 앱의 역할 | 알림(단골 약국 휴무, 연휴 운영), 홈 화면 위젯, 즐겨찾기·가족 프로필 → 모두 **재방문** 기능이다. 재방문 수요가 확인된 뒤에 투자하는 게 순서다 |

## 2. 검색 유입의 현실 점검

**검색 시장은 네이버가 주 무대다.** 2026년 상반기 네이버 검색 점유율은 64.28%이고([디지털데일리 2026-07](https://www.ddaily.co.kr/page/view/2026071214223169501)), 2025년 연평균은 네이버 62.86%, 구글 29.55%였다(인터넷트렌드, [인블로그 정리](https://inblog.ai/ko/blog/korea-search-engine-rankings)). 네이버 최적화가 필수이고, 구글도 30% 안팎이라 무시할 수 없다.

**큰 키워드에서는 상단을 차지하기 어렵다.** "약국", "문 여는 병원" 같은 큰 검색어는 네이버의 자체 영역(지도·플레이스, 블로그·카페)과 공식 채널이 상단을 차지할 가능성이 높다. 2021년 기사에는 네이버·다음에서 '명절병원'을 검색하면 E-Gen이 맨 위에 나온다는 안내가 있고([경향신문 2021-02](https://www.khan.co.kr/article/202102091200011)), 2023년 추석에는 다음이 자체 추석 탭에서 문 여는 병원·약국 정보와 E-Gen 바로가기를 제공했다([메트로서울 2023-09](https://www.metroseoul.co.kr/article/20230928500019)). 포털이 명절 의료 정보를 직접 보여주는 흐름이다. 둘 다 오래된 자료이고, 2026년 현재 네이버 검색 결과 화면은 직접 확인하지 못했다(브라우저 도구에서 네이버 검색이 차단됨 — 아래 확인 과제).

**그래서 노릴 곳은 롱테일이다.**
- 지역 × 과목 × 시간 조합: "수원 영통구 일요일 소아과", "마포구 설날 문 여는 약국"
- 기관명 + 시간: "○○약국 일요일 영업", "○○소아과 공휴일 진료"
- 구글은 롱테일 대량 페이지 색인에 상대적으로 유리하고, 네이버는 블로그·카페 시딩과 병행한다(세부계획 §8의 맘카페 시딩과 연결).

**새 도메인의 시간 문제.** 2026-10-18 기준 설 연휴(2027-02-06)까지 약 16주다. 세부계획대로 12월 말에 소프트 런칭하면 설까지 색인·순위가 잡힐 시간이 6주 남짓뿐이다. 검색용 페이지를 먼저 공개해 시간을 버는 것이 일정상 가장 효과가 크다.

## 3. SEO 설계

### 페이지 체계

| 페이지 | 규모 | 노리는 검색어 | 고유 가치(얇은 페이지 방지) |
|---|---|---|---|
| 기관 상세 | 병의원 79,006 + 약국 25,435 ≈ **10.4만** ([API 검증](API-검증결과.md)) | "○○약국 일요일", "○○소아과 공휴일" | 요일별·공휴일 진료시간표, 원탭 전화, **통화 확인 이력**, 근처 대안 기관 |
| 지역 랜딩 | 시군구 약 250 × 유형(약국·소아과·내과·이비인후과…) × 상황(일요일·공휴일·야간) | "영통구 일요일 소아과" | 그 지역의 해당 시간 운영 기관 목록, 등록률·확인 현황 |
| 연휴 특집 | 설·추석·성탄·신정 × 시도·시군구 | "설날 문 여는 약국 마포" | 복지부 지정 당번 정보 + 통화 확인 결과 |
| 가이드 | 수십 편 | "아이 열 39도 밤", "상비약" | 평시 유입. 세부계획 v2의 리텐션 콘텐츠와 겸용 |

- 진료시간 정보가 비어 있는 기관 페이지는 처음에는 검색 노출을 막고(`noindex`), 확인 데이터가 쌓이면 연다. 구글은 대량 생성된 저품질 페이지를 스팸 정책(scaled content abuse)으로 다루므로, 페이지 수보다 페이지마다의 고유 정보가 중요하다.

### 기술 원칙

1. **렌더링: 정적 정보는 서버에서, 현재 상태는 브라우저에서.** 진료시간표·공휴일 진료 여부·전화번호는 Next.js가 서버에서 HTML로 만들어 검색 로봇이 읽게 한다(주기적 재생성). 반면 "지금 영업 중" 배지는 캐시된 HTML에 넣으면 시간이 지나 틀린 상태가 되므로, 브라우저에서 현재 시각으로 계산하거나 경량 API로 덧씌운다.
2. **구조화 데이터:** schema.org `Pharmacy`·`MedicalClinic`, `openingHoursSpecification`(요일별), `specialOpeningHoursSpecification`(연휴), `telephone`. 검색 결과에 영업시간이 직접 노출될 여지를 만든다.
3. **네이버:** 서치어드바이저 사이트 등록, 사이트맵 제출(10만+ URL은 파일 분할), 수정일(`lastmod`) 관리. 네이버 검색 로봇(Yeti)의 자바스크립트 실행 범위는 공식 문서로 확인하지 못했으므로, 본문은 반드시 서버 렌더링 HTML에 넣는다.
4. **구글:** Search Console, 사이트맵, Core Web Vitals. 모바일 첫 화면 로딩 목표는 3초 룰과 같은 기준으로 잡는다.
5. **웹에서도 확인 루프가 돈다.** `tel:` 탭 후 페이지가 숨겨졌다가 다시 보이는 시점(`visibilitychange`)에 1탭 질문을 띄운다. 통화 연결 여부까지는 모르지만, 앱 없이도 MVP의 핵심 루프를 운영할 수 있다.
6. **PWA로 앱 수요를 미리 시험한다.** 홈 화면 추가와 웹 푸시(iOS는 16.4 이상에서 홈 화면에 추가한 웹앱만 지원)로 "단골 약국 연휴 운영 알림"을 먼저 제공해 보고, 수락률을 앱 착수 판단에 쓴다.

## 4. 앱으로 넘어가는 조건

**앱 착수는 설 연휴 실측 후 3월에 판단한다.** 설 연휴 이후 아래 지표를 보고 결정하고, 통과하면 4~6월 개발, 2027년 추석(9월 중순) 전 출시를 목표로 한다.

| 게이트 지표 | 의미 | 초기 기준(가설 — 소프트 런칭 실측 후 보정) |
|---|---|---|
| 연휴가 아닌 기간의 30일 재방문율 | 평시에도 다시 오는가 | 15% 이상 |
| "앱 알림 받기" 대기 신청률 | 웹에 버튼만 두고 수요를 재는 가짜 문 테스트 | 연휴 방문자의 3% 이상 |
| PWA 웹 푸시 수락률, 즐겨찾기 사용률 | 알림·즐겨찾기를 실제로 원하는가 | 추세로 판단 |

게이트를 통과하지 못하면 앱 대신 웹 리텐션(PWA 알림, 카카오톡 채널 알림)에 투자한다.

## 5. 앱이 해야 할 일과 프레임워크 영향

| 앱 요구사항 | 비중 | 프레임워크 영향 |
|---|---|---|
| 리스트·지도·원탭 전화 | 핵심 | 그래픽 부담이 낮아 어떤 프레임워크든 충분 |
| 지도(네이버·카카오) | 핵심 | 공식 SDK는 iOS·Android 네이티브용. Flutter(`flutter_naver_map`)와 RN(`react-native-naver-map`) 모두 **비공식 래퍼**이며 둘 다 2026년 4월까지 커밋이 이어지고 있다([gittrend](https://gittrend.io/repo/note11g/flutter_naver_map), [gittrend](https://gittrend.io/repo/mym0404/react-native-naver-map)). 래퍼 의존 리스크는 두 진영이 같다 |
| 푸시 알림 | 핵심(v2) | 모두 가능(FCM·APNs) |
| 홈 화면 위젯("가까운 문 연 약국") | 차별화 후보 | 어느 쪽이든 OS 위젯 코드가 일부 필요하다. Expo는 SDK 56에서 `expo-widgets`를 stable로 올려 iOS 위젯을 React로 작성할 수 있다([Expo 블로그 2026-06](https://expo.dev/blog/home-screen-widgets-and-live-activities-in-expo)). Flutter는 `home_widget` 패키지 + SwiftUI·Kotlin 작성 |
| 통화 결과 감지 | 확인 루프 정확도 | iOS는 CallKit의 `CXCallObserver`로 권한 없이 통화 연결·종료를 감지할 수 있어 "안 받음"을 자동 판정할 수 있다. Android는 통화 상태 조회에 전화 권한이 필요해 앱 복귀 시점 기반 판정이 현실적이다. 어느 프레임워크든 작은 네이티브 모듈로 해결된다 |
| 명절 당일 긴급 수정 | 운영 필수 | 영업 판정은 서버에서 하므로(§6) 데이터 오류는 서버로 고친다. 앱 UI 버그는 RN(Expo)은 EAS Update로 심사 없이 배포, Flutter는 Shorebird(별도 서비스) 필요, 네이티브는 스토어 심사를 기다려야 한다 |
| 큰 글씨·접근성 | P3 페르소나 | 모두 OS 글꼴 크기 반영 가능 |
| 웹과 코드 공유 | 개발 속도 | Next.js와 RN은 TypeScript로 타입·API 클라이언트·확인 루프 상태 로직·디자인 토큰을 공유한다. Flutter는 Dart라 공유할 수 없고, Flutter Web은 캔버스로 화면을 그려 SEO 웹을 대신할 수 없다 |

정리하면 이 앱은 **"얇은 클라이언트"**다. 무거운 그래픽이나 복잡한 애니메이션이 없고, 핵심 로직은 서버에 있으며, 플랫폼 고유 기능(위젯·통화 감지)은 어느 프레임워크든 작은 네이티브 모듈로 붙인다. 그래서 선택 기준은 성능이 아니라 **웹과의 공유, 운영 중 수정 속도, 팀 구성**이다.

## 6. 후보 비교

| 기준 | 네이티브 (Swift + Kotlin) | Flutter | **React Native (Expo)** | 웹뷰 래핑 (Capacitor 등) |
|---|---|---|---|---|
| 웹 포함 코드베이스 | 3개 | 2개(TS + Dart) | **1.5개(로직 공유)** | 1개 |
| 웹 코드 재사용 | 없음 | 없음 | 타입·로직·토큰 | 거의 전부 |
| UI 품질·반응성 | 최상 | 상 | 상 | 중(웹 수준) |
| 위젯·통화 감지 | 직접 구현 | 패키지 + 네이티브 코드 | `expo-widgets`(iOS) + 모듈 | 플러그인 |
| 지도 | 공식 SDK | 비공식 래퍼 | 비공식 래퍼 | 웹 지도 JS |
| 긴급 수정 | 스토어 심사 | Shorebird(유료 옵션) | **EAS Update 기본** | 웹 배포로 즉시 |
| 스토어 심사 리스크 | 낮음 | 낮음 | 낮음 | **애플 최소 기능 가이드라인(4.2) 반려 위험** |
| 필요 인력 | iOS·Android 개발자 각각 | Dart 개발자 | **웹(React) 팀이 확장** | 웹 팀 |
| 맞는 상황 | 위젯·워치 등 플랫폼 기능이 제품의 중심일 때 | 팀이 이미 Flutter 중심일 때 | 웹을 Next.js로 만들고 소규모 팀이 앱까지 맡을 때 | 게이트 전 '스토어 존재' 실험 |

## 7. 권고

**1안(권장): Next.js 웹 → React Native(Expo) 앱, 모노레포.**

```
apps/web      Next.js (SSR/ISR, SEO 페이지, 모바일 웹)
apps/mobile   Expo (React Native) — 리스트·지도·전화·푸시·위젯
packages/core 공통 타입, API 클라이언트, 영업 상태 표시 규칙, 확인 루프 상태 로직
packages/ui-tokens 색·글자 크기·간격(큰 글씨 모드 포함)
```

- 같은 팀이 웹에서 앱으로 넘어갈 수 있고, 웹에서 검증한 확인 루프 로직을 그대로 가져간다.
- iOS 통화 감지(`CXCallObserver`)와 위젯은 Expo 모듈로 붙인다.
- 웹 → 앱 전환 동선: 웹의 "알림 받기"에서 앱 설치로 연결하고, 유니버설 링크로 같은 기관 화면이 앱에서 열리게 한다.

**2안: Flutter.** 팀이 Dart·Flutter에 익숙하다면 앱 품질은 충분하다. 다만 웹(Next.js)과 앱이 별개 스택이 되어 확인 루프 로직을 두 번 구현하고, 긴급 수정에 Shorebird를 따로 붙여야 한다.

**네이티브를 지금 고르지 않는 이유:** 앱의 화면 대부분이 리스트·지도·버튼이어서 네이티브의 품질 이점이 사용자에게 잘 드러나지 않는 반면, 인력과 코드베이스가 두 배가 된다. 위젯·워치 같은 플랫폼 기능이 제품의 중심이 되면 그 부분만 네이티브 모듈로 쓴다.

**웹뷰 래핑은** 게이트 판단 전에 스토어에 존재해 보는 실험으로만 쓴다. 웹사이트를 감싼 수준이면 애플 심사에서 반려될 수 있어 푸시·위젯 같은 앱 고유 기능이 함께 있어야 한다.
